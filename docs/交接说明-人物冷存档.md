## 二、接手前必须知道的六件事

1. **用户明确要求：未得到「动手」指令前不要写代码。** 当前所有产出都只是设计。
2. **用户要求：改文档前先给方案，等确认再写。** 不要一边讨论一边落笔。
3. **一次只推进一个话题。** 不要一口气抛出多个问题；用户会按编号逐个过。
4. **用户基本不懂技术**：用大白话，先给结论和生活化比喻，术语首次出现要解释。
5. **语气要可爱**（颜文字、昵称都可以），**但技术结论、风险、未验证之处必须准确**，不能为语气放松。
6. **一切结论要有代码或文档证据**；没证据就说“不知道”或“未验证”。

## 三、这轮讨论里“最容易被后来者误解”的几个决定

> 详细定义都在设计稿对应章节，这里只点出反直觉的部分。

| 决定 | 反直觉在哪 | 章节 |
|---|---|---|
| 字典按**整数下标**，值靠 JSON 类型区分 | 值位置的“字符串＝原文、数字＝字典下标”；信度位是另一套规则，全是字符串 | 4.3 / 5.1 |
| 信度码含 `"N"` | `N`＝不标信度（信度开着也能用）；关信度时 **N 的值不参与排序、不被丢弃** | 5.1 / 5.5 |
| 单一字母槽位上限 50 | 内置已占 24 个；个人条目改用「该人物自己的条目下标（数字）」，不占字母池 | 4.2 |
| MVU 值不单独存 | 直接进条目数组，信度位写 `"9"`；关闭信度时 **MVU 值绝对优先** | 4.1 / 5.5 |
| 状态字段 0～3 | 把「离场/在场」和「是否 MVU 容灾」打包在一个数字里 | 第二节 |
| `onTurnSettled` **不是每轮必跑** | 它绑在「结算完」事件上；玩家把酒馆后台结算全关，它就不触发——这是刻意与官方对齐 | 10.1 |
| 已取消「蹭车」 | 不再用 `settlementSection` / `settlementTool`，全部走自己的常驻成员 | 10.3 |
| 容量提示一律不弹窗 | 只走「侧栏角标 + 酒馆状态页一节」，且必须写明“做了什么” | 3.5 |
| 条目分「唯一值」「计数方式」 | 关键度按值数算，但标了条目式的条目最多只贡献 1 分 | 4.2 / 第六节 |

## 四、还没定的事

1. **`onTurnSettled` 在“后台结算全关”时是否真不触发** —— 源码倾向“不触发”，实机未测；用户曾去问作者，未回。
2. **卡内映射（`extensions`）与绑定的优先级** 已定为「绑定 > 卡内 > 通用预设」，但**写卡后玩家还原原版**时的表现没细究。
3. **导出走浏览器下载** —— 标准做法，但酒馆文档没写这一条，未实测。
4. **多人物同轮召回时的排序细节**、连带召回的裁剪阈值，只有框架没有细参数。
5. **加值时效**：计划类条目的“到期”在无游戏时间时只能靠定期复查，复查轮数默认 10，未验证实际效果。

## 五、明确“第一版不做”的

按字数冷却、上下文占用感知、卡级人物档案绑定、向量召回、冷分片扩容 —— 都写在设计稿第十一节，不要再当待办捡回来。

---

## 六、动手时最先该验证的三件事

1. `onTurnSettled` 在结算全关时到底跑不跑（决定「自动判断」开关的真实边界）；
2. 前台工具 `toolModes` 只对 `play` 生效的实际表现；
3. 64 KB 是**字节**（已从源码确认），但实际写入 24 条目的册子能装多少人，仍需实测校准。
