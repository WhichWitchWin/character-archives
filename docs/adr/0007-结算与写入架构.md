# 0007 结算与写入架构：三档写入方式

- **状态**：已采纳
- **日期**：2026-10-31
- **supersedes**：设计稿 §10.2 的「两档自动判断」、§10.3 的「常驻成员 member + runTask」

## 背景：接口查证结果

写 M3/M4 之前把相关接口全查了一遍（`presets/tavern/skills/tavern-plugin/references/`）：

| 接口 | 事实 |
|---|---|
| `turnSection({ name, text, position? })` | `text` 可以是函数，收到 `{ gameId, turn, input }`，**`input` 是玩家这一轮的原文**；每轮算一次、结果随该轮保存；出错或 30 秒不返回只跳过这一段 |
| `onTurnSettled(handler)` | 收到 `{ gameId, turn, textVersion, greeting, text, rawText, card, variables, settledAt }`，**含结算后的变量**；「处理函数**不必等**完成才返回」—— 它是通知，**不阻塞、也不保证跑完** |
| `settlementTask({ name, title, phase, run })` | `run` 收到同一份内容 + `signal` + `runAgent`；**单个任务 5 分钟**；**「下一轮会等它们跑完」** |
| `runTask({ gameId, prompt, tools?, signal? })` | 一次性后台 Agent，返回 `{ text }`；带人物卡、世界书、最近两轮剧情；`tools` ≤ 8 个、一次最多调 16 次；10 分钟超时 |
| `getHistory({ gameId, from, to })` | 一次最多 50 轮，返回 `[{ turn, input, text, rawText }]` —— 批量读，不用一轮轮读 |
| `handle(name, handler)` | 参数 ≤ 256 KB，返回 ≤ 4 MB |
| `publishState({ gameId, name, data })` | data ≤ 256 KB，只存最新一份，只在内存 |
| `job()` / `member()` | **文档里不存在**（只在旧的 `plugin-design.md` 出现过） |

由此得两条结论：

1. 设计稿要的「常驻后台成员」没有落点 —— 每次写回只能用一次性的 `runTask` / `runAgent`，上下文得我们自己塞进提示词。
2. `onTurnSettled` 拿得到 `variables`，数据上够用；它的问题是**不保证跑完**，写回可能赶不上下一轮注入。

## 决定

### 1. `onTurnSettled` 只做程序类记账，永不 `await` 模型

三档里都注册。只干便宜、必须每轮、不能等的活：

- 更新在场名单 `anchors`；
- 写快照索引 `snapshots.index`；
- 记提示记录。

几毫秒，不碰模型，不让玩家等。

### 2. 模型写回分三档（设置项「写入方式」）

| 档位 | 名字 | 模型挂在哪 | 玩家等不等 | 特点 |
|---|---|---|---|---|
| ① | **异步结算**（默认） | `onTurnSettled` 里发起 `runTask`，不 await | 不等 | 可能**慢一轮**才进档案 |
| ② | **后台结算** | `settlementTask({ phase: 'after' })` | **等**（「下一轮会等它跑完」） | 保证本轮数据赶上下一轮注入 |
| ③ | **关闭** | 不调模型 | 不等 | 只做程序类记账；手动编辑与手动任务仍可用 |

- 「关闭」的准确含义是**不自动调模型判断**，不是插件不干活；
- 切换档位从下一轮生效（与其它设置项一致）。

> **命名风险**：②「后台结算」与酒馆自己的「后台结算」同名。设置项说明里必须写死一句：**「只影响本插件的人物册更新，不影响酒馆的变量结算」**（设计稿 §10.2 原本就强调过「两个结算要分清」）。

### 3. 异步档必须串行，且被拒要留痕

第 N 轮的写回没跑完，第 N+1 轮又发起 → 两个任务可能同时写同一份档案。

- `saveTurnData` 的 `textVersion` 校验会拒绝过期写入（`TAVERN_PLUGIN_STALE_VERSION`），**不会写脏**；
- 但会**丢一次写回**，所以：前一个没结束时不开新的（串行/跳过本轮），被拒时记一条提示，**不静默**。

### 4. 结构化输出用 `tools`，不解析自由文本

写回让模型调用一个工具（参数就是结构化的「新增 / 覆盖第 N 条 / 删除第 N 条 / 无变化」），比让它"输出格式正确的表格"可靠得多。工具 ≤ 8 个、一次最多 16 次调用，够用。

### 5. 不追求"常驻上下文"

`member()` 不存在，每次写回都是新会话。上下文靠我们自己拼：正文 + 该人物现有值清单（带序号，设计稿 §7.7 已经这么要求）。

## 后果

- **收益**：玩家默认不会被拖慢；需要准确性的人可以切到「后台结算」；`onTurnSettled` 顺带解决了"记账必须每轮、不能等模型"的问题；30 秒超时的焦虑消失（结算任务 5 分钟，`turnSection` 才是 30 秒）。
- **代价**：异步档下档案会慢一轮；后台结算档会让玩家等（任务越慢等越久）；三档多一份分支与测试。
- **被否决的方案**：
  - *只用 `onTurnSettled` 调模型*：不保证跑完，写回可能永久赶不上注入。
  - *只用 `settlementTask`*：每轮都让玩家等，即使多数轮次根本没人物变化。
  - *用 `job()` / `member()`*：接口不存在。

## 需要用户同步的设计稿

- §10.1 时序表：「结算完成 `onTurnSettled` → 交给常驻成员」改成「结算完成 `onTurnSettled` 记程序类账；模型写回按设置的三档走」；
- §10.2 两档 → 三档（异步结算 / 后台结算 / 关闭），默认异步结算；
- §10.3「`onTurnSettled` 是唯一落盘点 + 常驻成员」→ 改为「`onTurnSettled` 记程序类账；写回按档位分别走 `runTask` 或 `settlementTask`」；
- §12 补一条：结算任务 5 分钟、手动任务 10 分钟，`turnSection` 的函数是 30 秒。
