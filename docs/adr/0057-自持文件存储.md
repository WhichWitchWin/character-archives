# 0057 自持文件存储：快照与整局数据搬出酒馆

- **状态**：有效
- **日期**：2026-11-02
- **supersedes**：[ADR 0008](0008-条目定义的存放位置.md) 里「数据放酒馆 `saveTurnData`／`saveGameData`」的存储位置部分

## 背景

酒馆的会话存储有硬上限：

| 存储 | 上限 |
|---|---|
| `saveTurnData` | 每局 **2000 条**、合计 **8MB** |
| `saveTurnData` 单条 | **64KB** |
| `saveGameData` | **256KB**／局 |
| `savePluginData` | **256KB** 全局 |

我们每轮存一份完整快照。30 人 × 10 条值 ≈ 12KB／轮 → **500 轮就 6MB**，1000 轮直接爆。

叙事锚定的作者（Luker）在讨论里给了方向：

> 如果你要版本控制，又要存储容量，可能没必要完全使用 API 提供的会话版本存储，你完全可以自己维护文件结构存储，用 API 记录版本标识，而不必受到容量限制。

## 参考：叙事锚定怎么做

查了它的实现（`lib/data-store.js`、`lib/settlement/request-audit.js`）：

| 做法 | 细节 |
|---|---|
| 自己写文件 | `node:fs` 的 `mkdirSync`／`writeFileSync`／`readFileSync`，**完全不用** `saveTurnData`／`saveGameData`／`savePluginData` |
| 路径解析 | 结构发现：向上遍历找 `launcher-settings.xml` 读 `DataDirectory`；注释里定了三不原则——**不写盘符、不写用户主目录、不猜层级** |
| 清理 | `KEEP_TURNS` 轮次窗口 + `index.json` 记名单 + 写完顺手剪枝，剪掉的文件 `rm` |
| 删局 | **没接** `onGameRemoved` → 会留垃圾 |

最后一条我们**不学**：它没做删局清理，是它的债，不是我们要抄的设计。

## 决定

### 1. 内容写文件，酒馆只存指针

```
<插件目录>/data/
├─ games/<sessionId>.json              ← 整局数据（条目定义/字典/设置/flags/冷却）
├─ snapshots/<sessionId>/
│   ├─ index.json                      ← { version, turns: [{turn, file, hash}] }
│   └─ <turn>-<短哈希>.json            ← 每轮完整快照
└─ trash/                              ← 剪枝和删局的文件挪这儿（不硬删）
```

酒馆里：

```js
saveTurnData(turn) → { f: '42-a1b2c3d4.json', h: 'a1b2c3d4' }   // 约 40 字节
saveGameData()     → { v: 1, store: 'file', at: '…' }            // 约 50 字节
```

### 2. 版本正确性仍然交给酒馆

这是整个方案能成立的关键：**指针记录归酒馆管**。

- 回退／重生成 → 酒馆丢旧版本的记录 → 我们**读不到指针** → 自然也读不到"未来"的档案；
- 分叉 → 各分支各自一份记录；
- 只有"内容存哪儿"变了，"版本跟着正文走"这个承诺没变。

### 3. 清理：按轮次窗口，剪掉的挪 trash

- 默认保留 **200 轮**（`DEFAULT_KEEP_TURNS`），可调；
- 每次写快照后顺手剪枝，`cutoff = 当前轮 - 窗口`；
- **不硬删**，挪进 `trash/`——玩家手滑、出问题都还能翻回来；
- 接 `onGameRemoved`：整局目录挪进 trash。

### 4. 存插件目录，不跟酒馆数据区

`<插件目录>/data/`，用 `new URL('./data/', import.meta.url)` 定位——不猜路径、不做结构发现。

- **好处**：自己数据自己管，好排查；
- **代价**：重装插件时**如果清空目录就丢**。所以导出包（[ADR 0050](0050-导出必须带预设.md)）必须能带走全部内容——它本来就带。

### 5. 读的时候兼容旧格式

```
指针 {f,h} → 读文件
否则       → 当整份快照（旧数据，迁移期兼容）
```

老存档第一次跑就自动升格，不用玩家操作。文件丢了也不会崩，当作"这一轮没有快照"。

## 后果

- **收益**：容量不再有天花板。2000 轮 × 40B 指针 ≈ 80KB，离 8MB 差两个数量级。
- **收益**：每轮快照可以放心存全量，不用为了省空间做增量压缩。
- **代价**：数据从"酒馆内部"散到磁盘，出问题要自己翻文件。
- **代价**：重装插件（清目录）会丢；靠导出包兜底。
- **边界**：`trash/` 会慢慢长大，需要玩家自己清（或以后做成设置项）。

## 被否决的方案

- **继续用酒馆存储 + 压缩**：压缩会丢历史，而且复杂度不低。
- **完全不用酒馆记录**（纯文件）：回退/分叉后读到"未来"的档案，直接毁掉正确性。
- **放酒馆数据区**（像叙事锚定的结构发现）：它那套是为了"开发版和安装版行为一致"，我们放插件目录更简单，且用户明确要求不跟酒馆 data 走。
- **剪枝时硬删**：出问题没法救；挪 trash 成本极低。

## 待定

- 窗口 200 轮是否合适（可以做成设置项）。
- `trash/` 的清理策略（按大小？按时间？玩家手动？）。
- 整局数据要不要也做版本快照（现在只有一份最新）。
