# 0012 ADR 口径扩成行业标准：记录所有重要决策，不只记偏离

- **状态**：已采纳
- **日期**：2026-11-01
- **supersedes**：无。（替换项目约定里「ADR 只记与设计稿不一致」这条窄口径）

## 背景

项目原来的约定是：ADR **只记"实现与设计稿不一致"的地方**。这条约定省事，但有代价——**"为什么这样做"会大面积丢失**：

- 为什么用「快照 + 字典」而不是数据库或整册存储？
- 为什么字典是 `d[]` / `t[]` 两条并行数组，下标即号码？
- 为什么条目定义放整局数据而不放快照？（这条有 ADR 0008）
- 为什么零运行时依赖、不上构建？

这些决定散落在注释、交接文档和对话里，**没有一条可追溯的记录**。结果是每换一次接手的人（包括 AI 自己），都要重新推演一遍，甚至重犯已经否决过的方案。

行业里的 ADR 不是这么用的：**ADR 记的是"所有重要的架构/技术决策 + 为什么 + 后果"**，偏离只是其中一类。设计文档/RFC 放完整方案，ADR 放决策点，两者互补。

## 决定

### 1. 记录范围

ADR 记录**任何"重要决策"**，判据满足其一即算重要：

- 影响**结构或数据形状**（存什么、存哪、怎么编码）；
- 影响**对外行为**（召回、写回、面板显示）；
- 影响**性能或预算**（字数、调用次数、体积）；
- 影响**维护成本或协作方式**（谁维护哪份文档、测试策略）；
- **存在被否决的合理替代方案**（哪怕最后选了简单的那个，也要记"为什么不选另一个"）。

### 2. 一条 ADR = 一个决策

同一轮讨论里产生多个独立决策 → 拆成多份。不允许「一批决定」混在一份 ADR 里，否则以后无法单独 `supersedes`。

### 3. 固定六段模板

```md
# NNNN 一句话标题

- **状态**：已采纳 / 待定 / 已废弃
- **日期**：YYYY-MM-DD
- **supersedes**：无 / ADR NNNN 中「某条」

## 背景      —— 当时面对什么问题、有哪些约束、试过什么
## 决定      —— 分条写清楚，能落到代码/文档
## 后果      —— 收益 / 代价 / 边界
## 被否决的方案 —— 每个方案 + 为什么毙掉
## 待定      —— 编号的开放问题（Q1、Q2…）
```

### 4. 只增不改

已写条目正文保留。推翻旧结论时**新增一条**并标 `supersedes`，旧条目不动。

### 5. 元决策也走 ADR

"谁维护哪份文档""ADR 记什么"这类治理规则同样是决策，也要留痕（本 ADR 与 ADR 0013 就是例子）。

### 6. ADR 不是设计文档

ADR 只写"决定 + 理由 + 后果"，**不抄规格**。规格的唯一真源是设计稿。

## 后果

- **收益**：决策可追溯；新接手的人读一遍 ADR 就能重建思路；被否决的方案有了墓碑，不会反复重提。
- **代价**：ADR 数量会明显增加（v0.1 阶段估计要补 8～10 条），阅读成本上升——因此配一份**索引**（[docs/adr/README.md](README.md)）按"一句话"检索。
- **边界**：不是所有选择都值得写 ADR。纯实现细节（变量命名、循环写法）不进 ADR，只进代码注释。
- **被否决的方案**：
  - *维持「只记偏离」*：项目的多数决策根本没有对应的设计稿条文，等于永不入册；
  - *改用一份大的《决策日志》*：无法单独 `supersedes`，检索差，且容易变成流水账。
