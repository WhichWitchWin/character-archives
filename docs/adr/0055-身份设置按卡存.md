# 0055 身份设置：玩家称呼 ＋ 正文写作人称，按卡存

- **状态**：有效
- **日期**：2026-11-02
- **supersedes**：[ADR 0055 之前那版「主角与视角」放在整局设置里】——即本 ADR 上一轮刚加的 `identity.mainNames`（列表）与 `identity.viewpoint`（任意文本）

## 背景

上一轮把「主角的名字／视角人物」放进 `DEFAULT_SETTINGS`（整局数据）。用下来发现两处不对：

1. **它们是卡级设定，不是局级**——同一张卡换存档，"怎么称呼玩家""用什么人称"不该变；
2. **"视角人物"要的其实不是人名，是写作人称**——第一/二/三人称。原来那个文本框填的是名字，语义就错了。

## 决定

### 1. 两项，按卡存进插件数据（ADR 0054 的通道）

```js
pluginData.identity[cardKey] = { playerName: '林澈', person: 'second' }
```

| 项 | 类型 | 默认 | 作用 |
|---|---|---|---|
| **玩家默认称呼** | 文本（≤24 字） | **空** | 同名的人一律拒绝建档（[ADR 0024](0024-建档提前.md)）；也用于提示词「主角＝X」 |
| **正文写作人称** | 下拉：第一/二/三人称 | **第二人称** | 提示词「【本局视角】X」；代词：我／你／他 |

默认第二人称，因为这类卡正文普遍是"你推门进去"。

### 2. 提示词改成两个占位符

改造前（`docs/系统提示词.md` 第 26 行）：

```
【本局视角】第三人称；主角＝林澈。      ← 人称写死，只有名字是变量
```

改造后：

```
【本局视角】{{PERSON}}；主角＝{{PLAYER}}。
```

- `{{PERSON}}` ← 人称（第二人称…）
- `{{PLAYER}}` ← 玩家称呼（空则「主角」）

`buildSystemPrompt({ person, playerName })` 负责替换。

### 3. 界面位置：**档案界面顶部**，不是藏进设置页

玩家开局第一眼就该看到「你是（谁）」和「正文用（什么人称）」，改了立刻生效并按卡记住。

## 平台限制：抓不到玩家称呼

需求里要求"从酒馆『开局默认 → 基本信息 → 玩家默认称呼』抓，新卡自动填"。**做不到**——查过四条路，插件都拿不到：

| 接口 | 给什么 |
|---|---|
| `getTurnState()` | 轮次、忙碌状态 |
| `getRequestContext()` | `{ turn, input, sections }` |
| `getCardContext()` | 描述／性格／场景／世界书 |
| `getCard()` | 卡的原始数据，**不含**开局默认的称呼 |

真正的值在 `chat.macroState.userName`（酒馆内部结构），**没有暴露给插件**。

所以这一版：**留空 + 界面给提示**（标题里写明从哪儿抄）。等平台暴露了再改成自动填充。

## 后果

- **收益**：人称不再写死；玩家称呼一填，"拒建主角名"这条保护才真正生效（之前 `mainNames` 永远是空数组）。
- **收益**：按卡记住，换存档不用重填。
- **代价**：新卡要手填一次称呼（平台不给自动读）。
- **边界**：称呼只用于"拒建同名"和提示词里的「主角＝X」，**不参与人名匹配**。

## 被否决的方案

- **放在整局设置里**：语义是卡级的，换存档还要重配。
- **只用人称、不要称呼**：那"拒建主角名"就永远没数据，等于没有保护。
- **从卡名自动推断**：很多卡的卡名是 NPC，猜错会把最该建档的人永久拦死。
- **继续用「视角人物」这个说法**：它听起来是"某个人"，而实际要的是叙事人称，容易填错。
