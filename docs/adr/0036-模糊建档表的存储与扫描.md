# 0036 模糊建档表的存储与扫描

- **状态**：有效
- **日期**：2026-11-02
- **supersedes**：[ADR 0035](0035-候选改名模糊建档.md)「待定」里的第 1 条（存哪、什么格式）与第 2 条（谁更新已出现轮数）

## 背景

[ADR 0035](0035-候选改名模糊建档.md) 只把「候选」改名成「模糊建档」，**规格仍然是空的**。早先记的 TODO 是：

```js
{ 姓名, 首次出现轮, 次数 }
```

这是照搬"观察名单"的惯性写法，没想清楚**谁真的要用这个数**。查下来两条都不成立：

### 1. 「次数」判据根本用不到

判据③是这么写的：

> 出现 ≥ 2 轮（模糊建档表里出现过、本轮又出现，就算 2 轮）

它自己已经把算法写明了：**表里有他 ＋ 本轮又出现 ＝ 2 轮**。两个事实都是现成的，"3 次""7 次"这种精确数字一条判据都用不上。

### 2. 「轮次」不该出现在素材里

原素材是：

```text
【模糊建档】沈九（首次出现第 12 轮，已出现 1 轮）
```

这违反 [ADR 0025](0025-离场记录取代在场名单.md) 第三节：

> 轮次只供插件内部用，**绝不发给模型**。轮次是引擎概念，写进去还可能被它抄进剧情（"第17轮"出现在小说里就出戏）。

## 决定

### 1. 存储格式：整局数据，每人一个整数

```js
draft: { "卖炭翁": 30, "沈九": 33 }   // 姓名 → 入表轮次
```

- **只存「入表轮次」**；
- **不存次数**、**不存首次出现轮**、**之后也不更新**；
- 一人十几个字节，几百人几 KB，整局数据 256 KB 里可忽略。

### 2. 谁扫：程序，和「已建档人物」同一次扫描

`onTurnSettled` 里用 `match.js`（姓名／别名／单字）扫本轮正文，**一次扫描同时判两份名单**：

| 扫描对象 | 扫出来干什么 |
|---|---|
| 已建档人物 | 得出【本轮提到的人】＋状态，供模型判离场／回场（[ADR 0032](0032-判定素材带状态.md)） |
| **模糊建档人物** | 得出**本轮出现的**模糊建档名单，供模型按四条判据判够不够格 |

### 3. 两条路进表

1. **程序扫到**本轮出现的模糊建档人物 → 列进判定素材，模型判够不够格；
2. **模型自己发现**正文里的新面孔（程序没扫到的）→ 报 `{"动作":"模糊建档","姓名":"…"}` → 程序加进表。

程序是主路径，模型那条是兜底——**名字匹配漏了（代称、错字、没收录的别名）还有救**。

### 4. 素材只给名字

```text
【模糊建档】卖炭翁、沈九
```

判据③需要的两个事实（表里有他、本轮出现）模型都已经具备，多余的数字只会占位置、还可能泄漏引擎概念。

## 后果

- **收益**：存储开销几乎为零；素材最短；不再违反 ADR 0025。
- **收益**：一个整数就支撑判据③，**不需要每轮写盘**（入表那一刻写一次，之后不动）。
- **代价**：`入表轮次` 这个数在判据里用不上，只为将来的清理留着（见下方待定）。
- **边界**：程序扫不到的代称（"那老家伙"）不会出现在素材里；模型若自己认出来，仍可报模糊建档。

## 被否决的方案

- **存次数**：判据用不到，白占空间还要维护。
- **存首次出现轮**：素材里不该发，程序自己也不用它。
- **每轮更新入表轮次**：等于把它变成"最近出现轮"，多一次写盘，对判据没有帮助。
- **把整张模糊建档表发给模型**：几百个名字塞过去，和【已建档】全名单是同一个毛病——会让模型"看谁都像"（[ADR 0033](0033-判定素材删除已建档名单.md)）。

## 待定

- **怎么清理、保鲜轮数多少**——本次明确**不定**，留到下一轮单独讨论。
- 重名怎么处理（两个"卖炭翁"进表会不会撞）。
- 清理时删掉之后，那人再出现算"第一次"还是"回来过"，会影响判据③。
