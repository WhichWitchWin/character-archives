# 0015 采用 member（常驻后台成员）作为写回执行方式

- **状态**：已采纳
- **日期**：2026-11-01
- **supersedes**：无

## 背景

设计稿 §10.3 本来就写的是「`onTurnSettled` → 调起常驻后台成员（`member` + `runTask`）」，但旧交接文档留了一句「`job()`／`member()` 文档里不存在，别用」，导致这条设计一直悬着。

2026-11-01 直接查本地酒馆源码核实：

| 接口 | 位置 | 官方参考文档 |
|---|---|---|
| `member({name,title,system,tools})` | `tavern-plugin/lib/plugin-api.js:878` | **一个字都没写** |
| `job({...,member,...})` | 同文件 `:344` | 同样没写 |
| `settlementTask({...,member,...})` / `manualTask({...,member,...})` | `:889` / `:900` | 没写 |

结论：**源码有、文档没有**。交接那句只对"文档"成立。

`member` 的语义（源码注释 + 实现）：本插件自己的常驻后台 Agent，**每局一个独立 Session**，带自己的提示词前缀与缓存；注册时可给 `system`（1～上限字）和 `tools`；不给 `system` 就共享酒馆自己的后台前缀（人物卡、世界书）。注册后 `runTask({ member })` 就是往它投一条消息，**排队执行**，与酒馆自己的成员并行。

## 决定

**采用 `member` 作为写回与判断的执行载体**：

1. 插件加载时注册一个常驻成员（固定 `system` + 必要 `tools`）；
2. `onTurnSettled` 里 `runTask({ member })` 投递本轮的档案更新任务；
3. 结论仍走原来的校验 → 写人物书 → 存快照，唯一落盘点不变（ADR 0007）；
4. `settlementTask` / `manualTask` 需要时也可带 `member`。

## 后果

- **收益**：提示词固定 → **缓存命中率高**；同一局内能延续上一轮的归档上下文；不占用酒馆自己的成员；比"每轮一次性会话"便宜得多。
- **代价**：**官方未文档化 = 不保证**。酒馆升级若改掉/移除这个接口，需要退回"每轮一次性 `runTask`"。
- **边界**：必须处理生命周期——删局时释放成员、回退或重新生成时中止或丢弃过期结果（`textVersion` 校验已有）。
- **被否决的方案**：
  - *每轮一次性 `runTask`*（无 member）：行为等价但**每轮重建上下文**，贵且没有连续性——留作接口失效时的退路；
  - *自建 DSH 子 Agent*：复杂度高，当前不需要多步推理。
