# ADR 0101 主角必须在写入之前入档

- **日期**：2026-11-06
- **状态**：已定并已实现
- **相关**：[ADR 0085](0085-主角入档与召回规则.md)（主角入档与召回规则）、[ADR 0083](0083-写入流程-命题与指针.md)（写入流程）、[ADR 0100](0100-后台成员交卷按派发时定的盒子.md)（同一天修的相邻问题）

## 背景

后台档修好之后，结算能正常交卷了，但这一局的两条动作**整条被拒**：

```
写入动作被拒 2 条
原因：「认知里的「小s」不在档案里」
可用的栏目：["职业","性格","能力资源","当前处境","最后已知去向","后续计划","未了事项","关系"]
```

`小s` 就是本局的主角名，而快照里明明有 `["p0",1,"小s",""]`：

```json
{"p":[["p0",1,"小s",""],["p1",1,"沈清禾",""]], …,"pt":[["p1",1,…],["p1",2,…]]}
```

也就是说：**存盘的快照有主角，写入的那一刻还没有**——`pt` 里只有 p1 的两条指针，主角对这两件事的认知一条都没落下。

旧日志里同一个病：`认知里的「测试人」不在档案里`（那时的主角名是「测试人」）。所以这不是新 bug，是一直没人注意到的老 bug。

## 根因

写回的主流程里，`ensurePlayer`（保证主角 p0 存在、名字跟玩家称呼同步）排在 `applyWriteActions` **之后**：

```
runWriteback: … → 建素材 → 判人 → 应用人物动作 → 建素材(写入) → applyWriteActions … → ensurePlayer
                                                                                    ↑ 主角在这里才被建出来
```

于是这一轮：

1. **写入素材里没有主角**——模型看到的在场名单里没有 p0；
2. 模型报「谁＝小s」（这是对的，主角确实该知道）→ `resolvePersonRef` 在 `snapshot.p` 里查不到 → `writeActions` 判「认知里的「小s」不在档案里」→ **整条动作被拒**，连已经建好的那条命题的指针也一起丢掉；
3. 写入跑完，`ensurePlayer` 才把 p0 建出来并落盘——所以面板上"主角明明在档案里"，而错误信息说不在。

## 决定

**把主角的 `ensurePlayer` 提到「建素材之前」**（读完身份、算好视角之后，判人素材与写入素材都用得到）：

```js
const playerAtStart = ensurePlayer(snapshot.p, {
  name: identity.playerName,
  alwaysPresent: identity.person !== 'third',
})
snapshot.p = playerAtStart.persons
```

**轮末那次 `ensurePlayer` 保留**：模型可能本轮给主角改名、或在三人称下让他离场／回场，收尾还要再同步一次（`playerWasOffline` 的采样点仍在写入前，语义不变）。

## 为什么

- **不只是"修个报错"**：主角要是不在册，模型在素材里看不到「主角已经建档」，容易再报一次建档（撞名被拒）；召回、写入素材、面板显示也都会缺一角；
- **不在解析层兜底**：让 `resolvePersonRef` 看到「名字＝玩家称呼就直接返回 p0」也能消掉这句报错，但那时 p0 还不在 `snapshot.p` 里，写进去的指针会指向一个**当时不存在的编号**，只能靠后面 ensure 补——多一条隐式约定，不如直接把"主角常驻"提前落到数据上；
- **顺序就是语义**：ADR 0085 说「主角常驻、程序保证存在」，那它就得在整轮开始时就成立，而不是轮末才成立。

## 代价与边界

- **三人称不受影响**：`alwaysPresent` 传的是 `identity.person !== 'third'`，三人称下只保证存在与改名，不会把离场的主角拉回在场，`playerWasOffline` 的判断照旧有效；
- **空局那条 early ensure 保留**（`本轮没有可写入的人，跳过写入应用` 分支）：它负责第一轮就把主角落盘；
- **已有的坏数据不补**：这一轮丢掉的主角认知不会自动重算，重新生成那一轮或往后玩即可；
- **守卫**：`tests/playerOrder.test.mjs` 三条——① 没有 p0 时认知被拒（复现）② 有 p0 时正常落指针 ③ `index.mjs` 里 `ensurePlayer(` 必须排在 `buildCombinedPrompt(` 与 `applyWriteActions(` 之前（只比 `applyWriteActions` 会假通过，因为空局分支里本来就有一处 early ensure）；
- **未实测**：740 个测试全过只证明顺序与解析语义对；**真实对局里主角的指针能不能落下来，要重启 DSH 后再跑一轮看**（调试日志的拒绝原因里不该再出现「认知里的「××」不在档案里」）。
