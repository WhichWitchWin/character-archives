# 0003 设计稿由用户维护，ADR 只记「与设计稿不一致」的实现决定

- **状态**：已采纳
- **日期**：2026-10-31
- **supersedes**：第 1 条中「设计稿冻结、不再维护」一项

## 背景

0001 定下「设计稿冻结、只走 ADR」，理由是不想维护上千行的推演文档。

但用户随后**亲自更新了设计稿**（§3.3 写入策略、§3.4 每局总量删除规则、§3.5 容量兜底、必记事件表、§六 关键度），并要求「按新的来做」。这说明在本项目里，设计稿仍然是**活的规格来源**，只是维护者是人，不是 AI。

## 决定

1. **设计稿由用户维护。** AI 不主动修改它；确实需要改时，先提方案、等确认。
2. 实现与设计稿不一致时，**仍然写 ADR** 说明差异与理由，`supersedes` 指向被推翻的条目。
3. README / AGENTS / CONTRIBUTING 里「已冻结」的措辞一并改为「由用户维护」。
4. ADR 自身「只增不改」不变：推翻旧结论时新增一条并标 `supersedes`，旧条目正文保留。

## 后果

- 好处：规格只有一处真源（设计稿），不会出现两份互相打架的「现行结论」。
- 代价：设计稿与 ADR 可能短暂并存不一致 —— 读代码时若发现行为与文档不同，先按 ADR 编号找对应记录。
- 与 0001 不变的部分：三份活文档的分工（README / CONTRIBUTING / docs/adr）继续有效。
