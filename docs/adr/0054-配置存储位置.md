# 0054 配置存哪：默认插件数据按卡分区，存卡是可选

- **状态**：有效
- **日期**：2026-11-02
- **supersedes**：[ADR 0053](0053-快照地点与MVU勾选.md) 的「待定：勾选表存哪」

## 背景

勾选表（这张卡要收哪些 MVU 字段）**天然属于卡**——MVU 字段是卡的作者定的，换个存档还是同一批字段。所以第一反应是"存进卡里"。

但**存进卡 = 改卡**。查了酒馆接口：

```js
updateCardRaw({ card, operations, expectedRevision })
```

- `operations` 是 JSON Pointer 的 `set` / `delete`；
- **改的是卡的「工作副本」**，注释写明原始卡仍保留，玩家可以在酒馆里恢复；
- 传 `expectedRevision` 后带版本校验，卡被别处改过会抛 `REVISION_CONFLICT`。

也就是说技术上可行、也有安全网，但**它终究是在改玩家的卡**——这种事不该默认干。

## 决定

### 1. 默认：存在我们插件自己的配置里，**按卡分区**

```
savePluginData: { mvuChecklist: { "<卡id>": { "身份": true, "关系": true, … } } }
```

- 不碰卡文件；
- 按 `卡id` 分区，**同一张卡的所有存档共用一份**（符合"字段是卡定的"这个事实）；
- 换局不用重配，换卡要重配（`autoMap` 会先预勾一遍）。

### 2. 可选：玩家可以选「把这份配置存进卡里」

- 入口放在映射表设置里，一个按钮；
- **点击要二次确认**，文案说清：「会把配置写进这张卡；原始卡在酒馆里仍可恢复」；
- 存卡用 `updateCardRaw`，带 `expectedRevision`（先取 `cardRevision`），冲突就提示重试。

### 3. 读的时候谁优先

```
卡里的配置 > 插件数据里的配置 > 空（等 autoMap 预勾）
```

存卡之后，换设备 / 把卡发给别人，配置也跟着走。

## 后果

- **收益**：默认不碰玩家的卡；想带着走的人可以主动存进去。
- **收益**：按卡分区，换存档不用重配。
- **代价**：不动卡的时候，配置只活在这台机器的插件数据里（换设备要重配，或手动存卡）。
- **边界**：存卡改的是工作副本，原始卡仍可恢复——但玩家可能并不知道这点，所以确认弹窗必须写清。

## 被否决的方案

- **默认存卡**：等于默认改玩家的卡，太重。
- **存进"整局数据"**：换存档就丢配置，而 MVU 字段是卡级的，对不上。
- **存在插件文件夹里**：插件更新会整体替换文件夹，配置会没。
- **写死在某个卡 ID 上**：卡改名/移动就失联（§8.8 早有的结论）。

## 待定

- 写卡时的 **JSON Pointer 路径**（比如 `/extensions/dsh-tavern-character-archives/mvuChecklist`）——需要实测卡的 JSON 结构，确认 `set` 能创建不存在的中间节点。
- 卡被替换/重导后 `卡id` 变不变（若变，按卡分区的配置会失联，要考虑用卡名或指纹兜底）。
