# 0008 条目定义的存放位置

- **状态**：已采纳
- **日期**：2026-10-31
- **supersedes**：设计稿 §3.6 中「双字母条目（玩家自建）回退后从当前人物册删掉该条目」一行

## 背景

「条目码 ↔ 条目」的对照分三层，但只有前两层在设计稿里写清了：

| 层 | 存哪 | 设计稿怎么说 |
|---|---|---|
| 预设表（跨局） | 插件数据区 `savePluginData` | §8.8：**只存文字名，不存任何码**（映射表要跨局复用，码属于某一局） |
| MVU 映射表（跨局，跟卡绑） | 插件数据区 | 同上 |
| **该局的条目定义**（哪个码对哪个条目） | **没写** | §8.8 只说「在该局写入条目定义」 |

而快照结构是 `{ v, t, p }`，里面没有放条目定义的位置。

放不进去的原因：§3.6 规定「回退到没有该条目的快照 → 从当前人物册删掉该条目」，这等于要求条目**存在性**跟着快照走；但每份快照都带一份定义的话（24 条 × 约 50 字节 ≈ **1.2 KB/份**），2000 份就是 **2.4 MB**，占 8 MB 上限的 30%，代价太大。

## 决定

1. **该局的条目定义放整局数据**：新增字段 `entries`，形如

```js
entries: {
  a: { name: '姓名', prompt: '……', unique: true, mode: 'entry' },
  b: { name: '别名', prompt: '……', unique: false, mode: 'entry' },
  // …每个已分配的条目码一条
}
```

2. **快照里只放值，不放定义**。快照体积不变。
3. **条目码永不回收**：删掉条目、MVU 映射建了又不用，码都留着，不给别人 —— 否则历史快照会把值解成另一个条目。
4. **回退语义改为**：条目定义不随回退变化。回退到「那时还没有这个条目」的轮次时，界面会看到一个**空条目**，而不是条目消失。

## 后果

- **收益**：快照体积不变；条目定义只存一份（约 1 ~ 2 KB，整局数据 256 KB 里可忽略）；分叉、导出随整局数据自动带走。
- **代价**：回退后可能出现"空条目"（有定义、没值）。相比"条目凭空消失、历史显示错乱"，这是更可接受的降级。
- **被否决的方案**：
  - *每份快照带一份条目定义*：每份 +1.2 KB，2000 份约 2.4 MB，撑不起。
  - *快照带差量、按轮回放重建*：省空间，但每次读都要回放，复杂度不成比例。
- **连带规则**：预设表与映射表仍然只存**文字名**；把名字落到当前局的某个码，是"应用预设/映射表"那一步做的事。
