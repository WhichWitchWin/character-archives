# 0037 锁与眼睛解耦；锁不豁免沉降

- **状态**：有效
- **日期**：2026-11-02
- **supersedes**：[ADR 0031](0031-回头测试与沉降.md) 里「手动锁定 🔒 永不沉降」这一条；以及设计稿 §8.7 原规则「**眼睛闭上 → 锁自动锁上**，不允许出现『能写不能读』」

## 背景

原来 §8.7 是这么定的：

| 图标 | 管什么 |
|---|---|
| 🔒 锁 | 写入：锁上则禁止写入 |
| 👁 眼睛 | 召回：闭上则前台模型看不到 |

但加了一条联动：

> **眼睛闭上 → 锁自动锁上**，读与写同时关闭，不允许出现「能写不能读」。

这条联动把两个开关**绑成了一个**，等于只有一个自由度。当初的理由是"读写应该同权"，但**这个假设不成立**——两种"不同权"的状态都有真实用途：

| 想干什么 | 该锁 | 该闭眼 | 原来的设计能做吗 |
|---|---|---|---|
| 幕后黑手还没揭晓，别让正文主动念他；但剧情真提到时，细节要记下来 | ❌ 不锁 | ✅ 闭眼 | ❌ **做不到**（闭眼会自动锁上，写不进去） |
| 自己精心写好的档案，希望他照常出现在剧情里，但不许模型乱改 | ✅ 锁上 | ❌ 睁眼 | ✅ 能做到 |

而沉降那边还有一处类似的混淆：原来说「★ 重要人物、手动锁定 🔒 永不沉降」。

但**锁只是拦写入，沉降只是折叠显示、一个字都不改**，这是两件事：锁住的人照样可以被收进冷档，玩家点开还看得见。

## 决定

### 1. 🔒 锁只管写入，不影响召回

锁上 → 模型不能改这个人的档案；**他照常被召回、注入正文**。

### 2. 👁 眼睛只管召回，不影响写入

闭上 → 正文生成时看不见这个人；**但他的档案照样会被更新**。

### 3. 去掉联动，四种组合都合法

| 🔒 锁 | 👁 眼睛 | 效果 |
|---|---|---|
| 解锁 | 睁开 | 正常：能召回、能写入 |
| 锁上 | 睁开 | **只读**：照常召回，模型不改 |
| 解锁 | 闭上 | **只写**：不主动提起，剧情说了照记 |
| 锁上 | 闭上 | 全关：召回写入都停，只剩玩家手动编辑 |

### 4. 锁**不**豁免沉降

沉降公式去掉「未手动锁定」：

```
沉降 = gap ≥ 沉降轮数  且  非★
```

**只有 ★ 重要人物永不沉降。** 锁住的照样沉底折叠——因为锁防的是误改，不是防折叠。

### 5. 条目锁、值锁延后

现在只有**人物级**的锁，条目层和值层没有。要保护单条只能把整个人锁上，代价是他的其他条目也不再更新。

细化到条目/值 → [ROADMAP](../ROADMAP.md) **M5-6**。

## 后果

- **收益**：两个开关正交，能表达"只读""只写""全关"三种从前做不到的状态。
- **收益**：锁与沉降各归各位，不再互相牵扯。
- **代价**：玩家可能配出"看不见却在写"的状态，乍看有点怪——面板上要把两个图标的状态显示清楚，别让人以为坏了。
- **边界**：条目/值级锁没有之前，想保护单条只能锁整个人。

## 被否决的方案

- **保持「眼睛闭上→锁自动锁上」**：堵死"只写不读"，而这恰恰是"幕后黑手"的标准需求。
- **锁豁免沉降**：把"不许模型改"和"不许折叠"混成一件事；沉降不改任何数据。
- **干脆用「关掉整个写入方式」代替锁**：太粗暴，一关全关，连别人的档案也不更新了。
- **把眼睛和锁合并成一个「禁用」开关**：更简单，但丢掉四种组合里三种有用的。

## 待定

- **条目/值锁的继承与冲突**：人物锁上、条目解锁这种"子比父宽"要不要允许（见 M5-6）。
- **「改状态」算不算写入**：锁住的人，还能不能被模糊离场／回场改状态？倾向**不算**——锁防的是内容被瞎改，状态是剧情事实，应该跟着正文走。否则锁住的人永远停在"在场"，再也进不了召回池。
- 锁住的人还要不要出现在【写入】素材里（列了他的栏目清单、模型又不能改，纯浪费 token）。倾向**不列**。
