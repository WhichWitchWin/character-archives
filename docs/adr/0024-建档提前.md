# 0024 建档提前：非龙套就建档，离场只改状态

- **状态**：已采纳
- **日期**：2026-11-01
- **supersedes**：设计稿 §1「只维护**离场人物**；在场人物交给酒馆前台与人物卡原有机制」这一条边界

## 背景

原设计是「离场才建档」。这带来一个**冷启动**问题：

> 一个人从第 20 轮演到第 30 轮，第 31 轮起不见，第 34 轮判定离场要建档——
> 这时能拿到什么？本轮正文里**没有他**（模糊离场 = 他不在场、没被提），只能回看历史。

试过两种补救，都不好：

| 补救 | 问题 |
|---|---|
| 只取"最后一次在场轮"的正文 | **只一轮，必漏**——那 10 轮的戏全丢 |
| 回看整个在场跨度 + 按名字截取段落 | 成本高（每人几千字），还要处理"跨度太长"的截断，实现绕 |

**根因不是"没回看"，是建档太晚。**

同时核实了两条平台限制：

1. **后台模型不会自动拿到每轮正文**。`runTask` 只自带「人物卡、世界书、**最近两轮剧情**」（官方 `plugin-api-prompt.md:172`）。N=3 的模糊离场，两轮根本不够。
2. **我们和正文模型没有回话通道**。只有 `turnSection` 的**单向注入**，它写完就是写完；写入是另一个后台模型事后读文本做判断。

## 决定

### 1. 建档提前到"第一次被判定为非龙套"

不论此刻**在场还是离场**，都建档。之后按正常逻辑维护。

### 2. 在场人物照旧**不召回**

状态过滤即可（`0` 离场、`2` 离场·资料容灾才进召回池）。在场的人正文模型自己看得见，不需要我们塞。

### 3. 写入触发不变：**只在本轮"被提到"时发给模型**

不每轮把在场名单全发一遍——那样模型会回一堆「无变化」，纯烧钱。
唯一例外是 **MVU 值**：由程序按映射表直接抄入（信度位 `9`），不经过模型。

### 4. 离场判定拆成"程序初筛 + 模型判本轮"

| 谁 | 干什么 |
|---|---|
| **程序** | 用 `match.js` 扫最近 N 轮正文 + 在场名单 → 算出"连续 N 轮没出现"的**疑似名单**（纯统计，程序比模型准） |
| **模型** | 读**本轮正文** + 疑似名单 → 判"真离场／还在"，并抓强信号（告别、离开、死亡） |

这样不需要塞 N 轮全文，也不需要给模型配"查历史"的工具。

### 5. 人物级动作（补进动作集）

```json
{ "动作": "建档", "称呼": "老陈", "姓名": "老陈", "状态": "离场" }
{ "动作": "改状态", "人物": "老陈", "状态": "在场" }
```

- `姓名` 可留空 → 程序起临时称呼（`未命名·第12轮`），见 §2；
- **编号 `p7` 由程序发**，不交给模型；
- **与主角同名的，拒绝建档**（ROADMAP M4-12），并在面板/日志提示。

## 后果

- **收益**：档案从第一次出现就开始积累——**离场时不用回看、不用素材包、不建空壳**；离场只是改个状态。
- **代价**：快照里多出在场人物的条目（体积涨一些）；"是不是非龙套"要每轮判一次；召回必须**严格按状态过滤**，否则会把在场的人重复塞进正文。
- **边界**：在场人物的档案和酒馆前台是两套东西、互不可见，内容可能不一致——档案只记"事实"，靠来源标注（自述/他传/亲见）让正文模型自己判断。
- **被否决的方案**：
  - *只在离场建档*：冷启动，信息必丢；
  - *回看整个在场跨度*：能救，但贵且绕，等于用成本补设计的坑；
  - *每轮把在场名单全发给模型*：成本高、回报低（绝大多数是「无变化」）。
