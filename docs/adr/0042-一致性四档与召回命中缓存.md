# 0042 一致性改 4 档；召回命中缓存存「词」不存「条数」

- **状态**：有效
- **日期**：2026-11-02
- **supersedes**：[ADR 0041](0041-匹配与一致性拆开.md) 里「一致性 1 条 0.4／2 条 0.7／3 条以上 1.0」这一条

## 背景

### 1. 一致性 3 条就满分，太容易满

原档位是 1 条 0.4／2 条 0.7／3 条以上 1.0——**对上 3 条就顶格**。而一个人的档案里攒 3 条能对上的索引词并不难，导致"沾边"经常拿满，跟"点名"拉不开差距。

### 2. 更要紧的：只存「命中几条」，挑不出该给哪条值

详细档的规则是（§7.10.2）：

> 条目按「**本轮相关** → 预设顺序 → 信度」排

「本轮相关」靠的就是**命中了什么词**。只给一个数字 `clues: 2`，程序知道"命中 2 条"，但**不知道是哪 2 条**。

举个会出事的例子——老陈的档案：

| 条目 | 值 | 索引词 |
|---|---|---|
| 身份职业 | 旧港码头的账房 | 旧港码头 |
| **当前处境** | 在**旧港码头**养伤 | 旧港码头 |
| 未了事项 | 欠林澈一条命 | 林澈 |
| 性格 | 胆小怕事 | — |

正文：「**旧港码头**遭袭。」

- **知道命中的是「旧港码头」** → 程序能把「当前处境」推到最前 → 给模型「他正在旧港码头养伤」——**这才有用**；
- **只知道"命中 1 条"** → 只能按预设顺序给「身份职业」和「未了事项」——**跟这场袭击毫无关系**。

等于白给。

### 3. 两路来源会重复

召回只有两个输入（平台在 `turnSection` 只给玩家输入，拿不到历史正文）：

| 来源 | 怎么拿 |
|---|---|
| 本轮玩家输入 | 实时扫 |
| 上一轮正文的命中 | 读上一轮存下的小缓存 |

同一条索引词很可能两边都提到（玩家说"我去旧港码头"，上一轮正文也写了"旧港码头"）。**各自算一次，一致性就会被虚增。**

## 决定

### 1. 一致性改 4 档，4 条才满

| 对上条数 | 0 | 1 | 2 | 3 | 4 及以上 |
|---|---|---|---|---|---|
| 分数 | 0 | 0.4 | 0.6 | 0.8 | **1.0** |

步长 0.2，1 条仍保底 0.4（免得"沾一条"直接不召回）。

### 2. 缓存存「词」，不存「条数」

```js
flags.lastHits = {
  p7:  { hit: "alias", words: ["旧港码头", "林澈"] },
  p12: { hit: null,    words: ["一张欠条"] }
}
```

- `hit`：点名方式，供匹配分；
- `words`：命中的索引词**原文**，一份数据供两个用途——`words.length` 算一致性条数，词本身用来挑条目；
- **不存条数**：`words.length` 就是条数，存两遍迟早对不上。

### 3. 两路合并去重

本轮实时命中的词 ＋ 上一轮缓存的词，**合并后去重**再算一致性：

- 大小写不同算同一条（后传的覆盖前面的）；
- 一条是另一条的子串算同一条（「旧港」vs「旧港码头」，只留长的）。

实现上复用 `match.js` 已有的去重规则，并新增 `mergeClueWords()` 供接线处直接调用。

### 4. 匹配结果带上命中的词

`matchText()` / `matchPerson()` 的返回值新增 `clueWords`（命中的索引词原文），`clues` 仍保留（＝`clueWords.length`）。

### 5. 只回看上一轮

召回信号是**一次性消费**的：第 30 轮命中，第 31 轮就用掉，之后由冷却接管。再往前留只会让同一批人反复参与计算。所以 `lastHits` 只存一轮，每轮整体覆盖。

## 后果

- **收益**：详细档终于能挑对条目——"旧港码头遭袭"会给到"在旧港码头养伤"，而不是随机两条。
- **收益**：一致性满档更难（要 4 条），沾边召回更克制，跟点名拉得开。
- **代价**：`lastHits` 体积从"一个条数"变成"一个词表"，20 人约 400 字节，仍可忽略。
- **代价**：`matchText` / `matchPerson` 的返回多一个字段，所有旧断言要跟着加 `clueWords`（已同步，170 个测试全绿）。
- **边界**：`lastHits` 只管**已建档人物**；模糊建档的人走 `flags.draft`。

## 实测档位（关键度中位、普通角色、离场 20 轮）

| 场景 | 匹配 | 一致 | 总分 | 档位 |
|---|---|---|---|---|
| 本人出场 ＋ 对上 1 条 | 1.0 | 0.4 | 0.680 | 详细 |
| 别名 ＋ 对上 2 条 | 0.9 | 0.6 | 0.705 | 详细 |
| 本人出场，零关联 | 1.0 | 0 | 0.580 | 简单 |
| 只对上 4 条（没点名） | 0 | 1.0 | 0.580 | 简单 |
| 只对上 1 条 | 0 | 0.4 | 0.430 | 简单 |
| ★重要 ＋ 刚离场 ＋ 4 条 | 0 | 1.0 | 0.740 | 详细 |

**只沾边要进详细档，得关键度和时效都高**——中位角色最多到简单档。这是有意的："沾边"说明可能相关，还没到"该展开他的一生"。

## 被否决的方案

- **只存命中条数**：详细档挑不出条目（本 ADR 背景第 2 条）。
- **存命中位置、次数、上下文**：用不上，纯占空间。
- **两路各自算一致性再相加**：同一条词算两次，虚增分数。
- **回看最近 3 轮正文**：平台拿不到历史正文；而且信号早被消费掉了。
- **一致性保持 3 档**：3 条就满太容易，"沾边"经常跟"点名"打平。

## 待定

- **档位阈值仍要重校**：0.4／0.6／0.9 是照更早的算法定的。实测里"本人出场零关联"只有 0.580，差一点够不到详细档。
- 挑条目的具体排序细节（值内多条、条目间并列）等实机验证。
