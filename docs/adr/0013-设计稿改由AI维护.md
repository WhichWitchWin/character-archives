# 0013 设计稿改由 AI 维护

- **状态**：已采纳
- **日期**：2026-11-01
- **supersedes**：ADR 0003 中「设计稿由用户维护，AI 不主动修改」一项

## 背景

ADR 0003 定的是「设计稿由用户维护，AI 只提方案」。当时的理由是：设计稿是**活的规格来源**，用户亲自在改它。

现在情况变了：

1. **口径变化频率远高于文档更新频率**。仅 2026-11-01 一天，单字命中规则改了三轮、时效项重新定义——这些都只落在 ADR/对话里，**设计稿 §7.10 至今仍写着旧的 `exp(-0.01×轮数)` 等权公式**。
2. **漂移已经造成实际风险**：照设计稿实现的人（包括 AI）会做出与当前结论相反的东西。这不是假设，本轮就发生过——按 §7.10 的字面实现，冷角色会被系统性饿死。
3. 用户 2026-11-01 明确要求：**设计文档从现在开始由 AI 维护。**

## 决定

### 1. 设计稿由 AI 维护

不再需要逐次请示才能改设计稿。但**每次改动必须在同一次回复里说明：改了哪一节、为什么、对应哪条 ADR**，用户可随时回滚。

### 2. 设计稿只写当前最新状态

设计稿是**活的规格**，不写历史、不写"以前是这样"。历史与理由留在 ADR，设计稿只需在相关小节标注 ADR 编号。

### 3. 冲突时以设计稿为准

同一件事，若设计稿与 ADR 说法不一致，**以设计稿为准**——因为设计稿是被同步维护的那一份。发现不一致应立即修掉，并说明原因。

### 4. 流程：先 ADR，后设计稿

新决策 → 先写 ADR（决策 + 理由 + 后果）→ 再改设计稿对应小节 → 在 [ADR 索引](README.md) 里加一行。

### 5. 兜底机制

AI 有权限改上千行文档，风险是"改错没人挡"。三重兜底：

- **git**：每次改动可回滚（提交信息带 `docs(design):` 前缀）；
- **小节标注**：每个被 ADR 影响的小节都标 `见 ADR NNNN`，便于反查；
- **用户否决权**：用户口头否决即回滚，不需要理由。

## 后果

- **收益**：规格、代码、ADR 三者不再漂移；新接手的人只读设计稿就能上手，不必先考古对话记录。
- **代价**：AI 的写入权限扩大到核心规格文档；若判断失误，可能把错误结论"固化成规格"。靠 ADR 留痕 + git 回滚控制。
- **边界**：设计稿仍是**唯一规格真源**，ADR 不重复抄规格；两者职责不混。
- **被否决的方案**：
  - *维持「用户维护」*：口径漂移已经发生，且不会自愈；
  - *冻结设计稿、只走 ADR*（ADR 0001 的做法）：0003 已经验证过不可行——规格散在几十份 ADR 里，读不出全貌。
