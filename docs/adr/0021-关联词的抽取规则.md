# 0021 关联词的抽取规则

- **状态**：已采纳
- **日期**：2026-11-01
- **supersedes**：无（补齐设计稿里"关联线索"从未定义的部分）

## 背景

「关联线索」同时被两根钉子用着：**匹配**（每条 0.5、递减累加）和**一致性**（对上条数 → 0.4/0.7/1.0）。但整套设计里从来没定义过"一条线索是什么"，`match.js` 只是收一个数组，谁生成它一直是空的。

试过两条更简的路，都不行：

- **值即关键词**（把值掐成短词，值本身当关联词）：反直觉、玩家维护成本高、看档案时看不懂；
- **只关联人名**（程序扫名字表）：正文只提地点、不提人名时彻底召不回——而离场人物恰恰最常在"被人议论"时出现。

结论：由**写入时的那次模型调用**顺带抽词。

## 决定

### 1. 时机与形态

写入同一次调用里，每条值多带一个字段，**不额外调用**：

```json
{ "动作": "新增", "栏目": "最后去向", "值": "旧港码头", "线索": ["旧港码头"] }
```

### 2. 只抽四类专名

| 类型 | 例 |
|---|---|
| 人名 | 林澈、林昭（别的 NPC、主角都算） |
| 地名／场所 | 旧港码头、南洋商行、西市 |
| 组织／势力 | 海关、商会、黑衣卫 |
| 独特物件／宠物 | 玉牌、煤球（有名字的东西） |

### 3. 黑名单（不抽）

| 类型 | 例 | 为什么 |
|---|---|---|
| 代词 | 他／她／他们／那个 | 满篇都是，抽了等于白送分 |
| 泛指 | 那个地方、北边、某人 | 正文里几乎不会原样出现 |
| **通用状态** | 受伤、生气、活着、死了 | 谁都可能受伤 |
| 通用职业 | 账房、掌柜、伙计 | 除非和专名连用（`旧港码头的账房` → 抽「旧港码头」） |
| 通用物件 | 刀、剑、酒、钱 | 同上 |
| 评价／情绪 | 老实、可疑、善良 | 不是可检索的东西 |

### 4. 数量与形态

- **0～2 个**，宁少不多；
- 长度 **2～10 字**；
- **必须是值的原文片段**，不加修饰；
- 优先级：**人名 ＞ 地名机构 ＞ 物件**。

### 5. 程序校验六道

```
① 不是字符串 / 空串           → 丢
② 归一化后不是值的子串         → 丢（防幻觉）
③ 长度 <2 或 >10              → 丢
④ 命中黑名单                  → 丢
⑤ 归一化去重（全半角、大小写）  → 合并
⑥ 超过 2 个                    → 截断
```

全被丢掉也正常——这条值就是没有关联词，不报错、不影响写入。

### 6. 条目分工：可检索型 / 纯描述型

| 角色 | 干什么 | 典型条目 |
|---|---|---|
| **可检索型** | 提供关联线索，让"没点名也能召回"成立 | 姓名、别名、最后去向、未了事项、关系 |
| **纯描述型** | 只负责注入内容，不参与匹配 | 性格、14 条外貌、能力资源、后续计划、纯状态的当前处境 |

**纯描述型不是缺陷**：正文里光说"一个长脸的男人"，本来就不该断定是某人。它们要靠"值里带专名"（`在旧港码头养伤` 而不是 `受伤`）才获得检索力——这属于书写规范（ADR 0022）的范畴。

### 7. 存储：按值文本缓存

存在 `savePluginData`（≤256 KB，来源：`plugin-data-store.js:6` 的 `MAX_PLUGIN_DATA`）：

```js
{ "旧港码头": ["旧港码头"], "旧港码头的账房": ["旧港码头"] }
```

- 键是**归一化后的值文本**，值是关联词数组；
- 跟着**内容**走，回退、分叉都不会错位；跨局可复用；
- 满了 LRU 淘汰；未命中就是"暂时没有关联词"，不漏不错。

## 后果

- **收益**：关联线索第一次有了明确来源；抽取可校验（子串）、可缓存、不占快照；纯描述型条目的定位也清楚了。
- **代价**：写入输出每条值多约 10 字符；缓存要管 256 KB 和 LRU；存量值（老档案、手改值）没有关联词，只能懒着补或手填。
- **边界**：模型抽得不准则召回不准——所以黑名单和三道校验都不能省。
- **被否决的方案**：
  - *值即关键词*：反逻辑、玩家看不懂；
  - *只关联人名*：地点/物件类正文彻底召不回；
  - *额外跑一次抽词调用*：白花钱，写入本来就是一次调用。
