# 0027 写入方式两档：自动维护 / 关闭

- **状态**：已采纳
- **日期**：2026-11-01
- **supersedes**：ADR 0007 的第 2 条「模型写回分三档（子代理／后台／关闭）」

## 背景

ADR 0007 定三档时，整篇建立在一个**后来被推翻的前提**上：

> "`member()` 不存在，每次写回只能用一次性会话"（ADR 0007 行 20／24／71）

核实结果：**`member` 存在**，是"每局一个常驻会话、任务排队执行"（ADR 0015）。这带来两个变化：

1. 常驻成员**天然串行**——ADR 0007 第 3 条"防止两个写回同时写同一份档案"自动解决；
2. 既然能常驻，就不必每次重建上下文，写回的成本与延迟都降下来了。

另外两条本轮已定的前提：

- **接受"滞后一轮"**（判定 + 写入串行，不阻塞下一轮）；
- "同步等"意味着**每轮玩家都要等模型跑完**，而档案更新对玩家**不可见**——等得不值。

## 决定

### 1. 只留两档

| 档 | 名字 | 行为 |
|---|---|---|
| **①（默认）** | **自动维护** | 每轮结算后：程序记账 → 常驻成员跑「判定 → 写入」→ 校验 → 落盘。**可能滞后一轮** |
| **②** | **关闭** | 不调模型。**程序类记账照常**（离场记录、快照索引、MVU 抄入、提示记录） |

设置项名称：**自动维护**。

### 2. 上一轮没跑完 → 跳过本轮

常驻成员里的任务是排队的。若上一个还没结束，**不再往里塞**，记一条提示——否则会越积越多，越跑越旧。

### 3. 「关闭」不等于插件不干活

- 不自动收录、不自动更新条目；
- 但 MVU 值仍由程序按映射表抄入（信度位 `"9"`，不经过模型）；
- 手动编辑、手动任务照常可用。

## 后果

- **收益**：少一套分支与文案；不阻塞玩家；并发问题由 member 的排队天然解决。
- **代价**：需要"立刻生效"的玩家没有选项（只能等下一轮）；滞后一轮始终存在。
- **边界**：关闭期间档案不会自动变，但快照索引与离场记录继续维护，回退/分档逻辑不受影响。
- **被否决的方案**：
  - *保留三档*：同步档要玩家每轮等，而收益不可见；多一套分支与测试；
  - *再加一档"同步"*：同上；
  - *完全不给开关*：玩家无法在"省 token"和"自动维护"之间选择。

## 待定

无。
