# 0029 子代理档的一轮流程：先判定、后写入，正文只发一次

- **状态**：已采纳
- **日期**：2026-11-01
- **supersedes**：无（细化 ADR 0028 的子代理档）

## 背景

子代理档每轮要问两次（判定 + 写入）。同一个会话里**第二次不用重发正文**，所以两次不贵；但**顺序**会影响一件事：

> 本轮新建档的人，能不能在同一轮就把条目写进去？

- **先写入**：此时新人还没档案、没有栏目清单可发 → 只能等下一轮 → 冷启动问题又冒头。
- **先判定**：判定建完档，第二次就能给新人一份空栏目清单，让他当轮新增条目。

## 决定

### 1. 每轮两次 followup，正文只在第一次发

```
消息 1：正文全文 + 当前 gt + 【判定】
        → 返回：建档 / 改状态
消息 2：（不重发正文）涉及人物的栏目清单 + 【写入】
        → 返回：值级动作数组
```

### 2. 顺序固定：判定 → 程序执行 → 写入

```
① 程序初筛（扫最近 N 轮、算疑似离场）
② followup#1 判定
③ 程序执行：发编号、建档、改状态、写离场记录
④ followup#2 写入（清单里包含刚建档的人）
⑤ 校验 → 落盘（唯一落盘点）→ 存快照
```

### 3. 写入的清单要包含"刚建档的人"

新人此时**栏目全空**，所以我们给他的是「栏目定义 + 空列表」，让模型用「新增」把本轮观察到的写进去。

### 4. 被判离场的人，本轮照样写

"他走之前说了什么"正是最该记的；而且这时写的内容还赶得上下一轮召回。

### 5. 失败与生命周期

| 情况 | 处理 |
|---|---|
| 判定失败/超时 | **仍对已建档的人跑写入**（别浪费这一轮），只是本轮没有新建档 |
| 写入失败/超时 | 本轮没有条目更新，记提示，**绝不阻塞下一轮** |
| 回退 / 重新生成 | `agent.cancel()`；落盘前用 `textVersion` 校验，过期结果丢弃 |
| 删局 | `handle.dispose()` 释放子代理 |
| 上一轮没跑完 | **跳过本轮**，记提示（不排队堆积） |

## 后果

- **收益**：新人当轮建档当轮写入，冷启动彻底消掉；写入清单被判定收窄；正文只发一次。
- **代价**：两次调用串行 → 延迟略高（可接受，反正滞后一轮）。
- **边界**：判定失败时新人要等下一轮；这是刻意选择——"不为了一次判定失败就阻塞整条链"。
- **被否决的方案**：
  - *先写入后判定*：新人晚一轮建档，冷启动问题复发；
  - *合并成一次调用*：输入会同时包含"全轮正文 + 全量栏目清单"，且输出要混两组结构，模型出错面变大。
