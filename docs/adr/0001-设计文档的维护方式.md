# 0001 设计文档的维护方式

- **状态**：已采纳
- **日期**：2026-10-31
- **supersedes**：—

## 背景

接手时唯一的设计来源是 `docs/人物冷存档插件-设计稿.md`（1337 行）。它记录的是讨论阶段的推演过程，体量大、结论分散，随着代码落地会不断出现「当初这么定，现在不那么做」的地方。

如果继续维护它，每改一次代码就要回头改一份上千行的推演文档，改完还看不出哪条是现行结论 —— 文档会变成第二份需要同步的"代码"。

## 决定

1. **设计稿冻结**，不再维护。它作为「当时的想法」的历史基线保留，不删、不改。
2. 往后任何与设计稿不一致的决定，写成 **ADR** 存进 `docs/adr/`，一条决定一个文件。
3. 现行结论以 ADR 为准；活文档只有三份：

| 文件 | 回答什么 |
|---|---|
| `README.md` | 是什么 / 怎么装 / 怎么用 |
| `CONTRIBUTING.md` | 怎么参与开发（环境、调试、测试、路线） |
| `docs/adr/` | 为什么这么做 / 改过什么 |

4. 写法沿用行业惯例：
   - 文件名 `NNNN-简短标题.md`，四位编号递增，不复用编号；
   - 正文四段：背景 / 决定 / 后果（另加 `状态`、`日期`）；
   - **只增不改**：推翻旧结论时新增一条并标 `supersedes: 第 N 条`，旧条目正文保留。

## 后果

- 好处：代码改动只需新增一条 ADR，不必回头维护上千行的推演文档；「为什么这么做」有唯一去处。
- 代价：读代码的人要知道「现行结论在 ADR 里」，不能只看设计稿；ADR 会越积越多，需要时按编号或关键字检索。
- 不采用的两条路：
  - **继续维护设计稿**：每次改动都要动一份大文档，容易漏同步，且看不出哪条是现行结论。
  - **只写 CHANGELOG**：CHANGELOG 记的是「哪个版本改了什么」，回答不了「为什么这么定、否掉了什么备选」。等真要发版本时再单独加 CHANGELOG，两者不冲突。
