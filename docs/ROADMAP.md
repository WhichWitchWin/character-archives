| M5-1 | 插件独立设置页 | ✅ | 设置项分「召回／写回／界面／容量」四组；每项有默认值与一句话说明；改动即时生效 | 设计稿 §8.6 |

| M5-4 | 压缩人物册历史 | ⬜ | 按设计稿 §3.7 合并旧快照，索引同步更新，召回结果不变 | 设计稿 §3.7 |
| M5-5 | 冷启动引导 | ⬜ 下一版 | 首次安装时说明三件事：数据存哪、什么时候召回、怎么关；可跳过 | 新增（用户可删） |
| M5-6 | **条目锁与值锁** | ⬜ | ① 条目行、值行各有一个小锁，可**单独**锁住；② 锁住的条目／值**不接受模型写入**——新增／覆盖／删除／判定一律丢弃并记日志；③ **下层继承上层**：人物锁上＝其下全部锁住，条目锁上＝其下所有值锁住；④ **锁不影响召回**，照常注入正文；⑤ 存整局数据、不写快照、回退保持原样；⑥ 面板上锁住的条目／值有明确视觉标记 | ADR 0037 |

| M5-8 | **形象包入口（兼容配图插件）** | ⬜ 下一版 | 14 条外貌栏目（`lib/presets.js` 的 `APPEARANCE_NAMES`）**数据在、但没有任何入口**：建局固定只取 8 条通用栏目，当年控制它的「启用人物外貌条目」设置项已随清理删掉（2026-11-06 核）。要做的：① 预设视图里能看到这 14 条（名字＋提示词，只读）并能**一键加进当前预设**（写全局／按卡，跟现有预设保存同一套）；② 已启用时能移除，但**该栏目里还有命题时要拒绝**并提示先删命题（否则栏目码成孤儿，面板会显示成一串码）；③ 修掉提示词生成公式的 bug（现在产出 `" SFW按 danbooru 标签化书写…"`，有前导空格、`背面` 没吃掉），并保证每条 ≤30 字；④ **默认不带**，玩家点了才进预设（14 条会占工单字数与召回预算） | 2026-11-06 对话 |
| M5-9 | **主角也是人物：让他自己的档案写得进来** | ⬜ | 现象（2026-11-06 实测）：`targets: 2` 证明主角 `p0` 已在在场名单与写入素材里、模型也用 `谁:"小s"` 给他记过认知，但**从不产出 `关于:主角` 的命题**——主角的栏目永远是空的。查过不是被拒（`拒绝 0`）、也不是认不出人（工单写着「主角＝小s」）。原因：素材按「他知道什么」组织，主角块里只有关于别人的命题；正文第二人称从不出现主角名；提示词没有一句说「主角也要写他是什么样的人」。要做的：① 系统提示词加一条——主角同样是人物，职业／性格／能力／处境／去向照栏目写，`关于` 写主角档案名、`认知` 写 `{谁:主角名, 来源:"自己"}`；② 若①不够，再给 `buildWriteMaterial` 传 `playerId`，在主角块头标「（主角本人：他自己的档案也要写，别只写别人）」；③ 验收：连玩两轮，主角档案里出现至少一条关于他的命题，且不误伤 NPC 的写入 | 2026-11-06 对话 |

## 六、已设计好、第一版砍掉的功能

> 这些**讨论完了、方案留着**，只是 v0.1 不做。以后要做，直接照这里实现。

### 6.1 完整召回

**定位**：奢侈品。给"这人我熟透了"的极少数场合，**人多的时候永远轮不到**。

| 项 | 内容 |
|---|---|
| **三重门** | ① 全局开关「启用完整召回」打开 ② 该人物被标 ★ ③ 总分 ≥ **0.90**。缺一，最高只到详细 |
| **内容** | 该人物**所有勾选条目的所有值**（不挑、不筛） |
| **装配位置** | 四步流水的**最后一步**：先保底简单 → 升详细 → 填提示 → **还有预算才升完整** |
| **名额** | 每轮**最多 2 个** |
| **每人上限** | 800 字符（未定稿） |
| **代码现状** | `recall.js` 的 `TIER.full = 0.9` 与 `tierOf({ fullAllowed })` 已就位（默认 `false`＝永不触发）；**装配层不实现** |

**为什么砍**：

1. 三重门几乎不触发；
2. 装配排最后，人一多必被挤掉；
3. 一次塞 800 字，大半是主角用不上的内容（外貌标签、过期旧值、互相矛盾的旧说法）；
4. 还要单独实现"全档案怎么拼"这一整层。

**真要捡回来时的前置**：先做装配层的四步流水线（现在只有三步）+ 每人上限。

### 6.2 人物信任标签

**想法**：给人物打「可信／中性／不可信」，以他为来源的值**派生**成真／未定／假（不写穿存储）；值自身的 `+/-` 证据优先；自述也算他说的。

**2026-11-01 讨论后不采用**，两个硬伤：

1. **视角不兼容**：插件要同时支持第一／第二／第三人称。第一、二人称主角永远在场，"亲眼见到"满街都是；第三人称主角可能根本不在场。同一套判据在三种视角下含义完全不同。
2. **"骗别人不骗你"**：NPC 完全可能对别的 NPC 撒谎、对玩家说真话。人物级标签一锁"可信"，等于把他**对所有人**说的话全判成真——玩家明明知道他在骗别人。

**若要做，得先解决**：标签是"他对谁说的"分级？还是只保留逐条覆盖（值的 `+/-`）？

**结论**：默认信度仍是**未定**（ADR 0019 不变），本功能延后。

### 6.3 约定到期与兑现（**建议单独做一个插件**）

**想法**：约定类条目（未了事项、后续计划）到期或兑现时，由模型判断"兑现没"，程序打标记（带兑现时刻的 `gt`），召回时提示"这条可能已过期/已兑现"。

**为什么不在本插件做**（2026-11-01 决定）：

1. 模型没有"轮次"概念；没有 `gt` 的游戏更无从判断——硬做等于让它瞎猜；
2. 判"到期"就得定期复查（每 N 轮把所有约定过一遍），成本随档案规模线性增长；
3. 标记的回退语义很麻烦：存快照占体积，存插件数据又得配一整套"回退只记、跑一轮才清理"的机制（照 ADR 0009 那套）；
4. 这是"时间与承诺管理"，和"人物冷存档"是两个关注点，塞一起会让主插件变重。

**真要做时，方案要点**：

- 动作集加「兑现」：**模型只判"兑现没"**，时间和轮次由程序取；
- 标记存 `savePluginData`，按 `gameId → 人物 → 条目码＋值文本` 定位（**不用序号**，序号会变）；
- 回退：只记 `rollbackAt`，**回退后跑一轮**才清理 `turn > rollbackAt` 的标记；
- 分叉是**新 gameId**，标记天然不跟过去；
- **没有 `gt` 的游戏直接关闭该功能**。

> 本插件里 `gt` 的语义因此定死：**只表示"这条值被收进来的时间"**，不表示"事情什么时候发生"，也不用来判到期。
